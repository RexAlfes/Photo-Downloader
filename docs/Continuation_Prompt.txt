CONTINUATION PROMPT - Photo Downloader (current release: version 0.1.4.1 = major 0, minor 1, revision 4, build 1; documents name it 0.1.4; next bundle 0.1.5.0)
Paste this into a new chat together with the latest PhotoDownloader.<version>.zip.

I am continuing development of "Photo Downloader", a free GPL v3 photo-ingest tool for Windows 64-bit written in Lazarus 4.8 / FPC 3.2.2 (objfpc). Forms are built in code (.lfm conversion is deferred). A Linux version is planned later, so keep new code portable where practical. The attached zip is the current source; unzip it and work from it. Build 42 is the baseline code.

STANDING RULES
1. Deliver a bundle only when I say "create bundle". Bug-fix reports get a delivery right away. "No new delivery needed yet" means update the working copy only.
2. VERSIONING: the version is major.minor.revision.build, stored in PhotoDownloader.lpi (Project Options > Version Info: MajorVersionNr absent = 0, MinorVersionNr 1, RevisionNr, BuildNr). Every bundle raises the REVISION by one and resets the BuildNr to 0 (user's decision 2026-11-11; set BuildNr to 0 just before the bundle compile, which makes the program x.y.z.0 and leaves 1 in the lpi; bundles up to 0.1.4.1 used build 1); my Lazarus then counts the build number up with each compile (AutoIncrementBuild stays on) until the next bundle. History: up to 0.1.0 build 57 only the build number counted; 0.1.0.58 was the last bundle of that style (revision 0, build 58); 0.1.1.1 is revision 1, build 1; 0.1.2.1, 0.1.3.1 and 0.1.4.1 followed; the next bundle is 0.1.5.0, then 0.1.6.0 ... (numbering confirmed by me). AppVersionString (uVersion.pas) shows it in the About box and the splash screen. Bundle name: /mnt/user-data/outputs/PhotoDownloader.{major}.{minor}.{revision}.{build}.zip, for example PhotoDownloader.0.1.1.1.zip (no spaces). Remove older zips from outputs; also copy the new release notes (GitHub/Release_Notes_<version>.md) and README.md to outputs. Once the code is stable and tested the revision/build are updated and the zip is packed for the GitHub upload (release asset names PhotoDownloader.<version>.Win64.exe / .Win64.zip / .linux64.tar.gz, tag v<version>).
3. Zip contains the single top-level folder PhotoDownloader/ with source, linux/ (launcher kit), Claude Prompt/, docs/ (Specification_Current .md/.odt, Settings_File.md, Continuation_Prompt.txt, Photo_Downloader_Launch_Materials .txt/.docx and _Tester_Kit.docx), GitHub/ (Release_Notes_<version>.md, older Release_Notes_0.1.0_buildN.md stay, Git Instructions.txt, GitHub_About.txt, docs/ with User_Manual .md/.odt and index.html), .github/ (FUNDING.yml, workflows/build.yml), .gitignore, PhotoDownloader.ico, PhotoDownloader.lpi, PhotoDownloader.lpr, README.md, THIRD_PARTY_NOTICES.md, third_party/XelHeic/. Exclude */lib/*.
4. Keep every document in step each bundle (titles name the version without the build, for example 0.1.2): README, spec (header, history row, status tables), Settings_File.md, launch materials (txt + both docx), Git Instructions (commit message, tag), website, release notes. Every document except README.md is kept as .md, .docx and .odt: run python docs/make_formats.py.
5. No Breeze or "Downloader Pro" wording. Defaults must be generic (nothing specific to my computer).
6. Claude Code works on my computer: compile with lazbuild (lazbuild and the IDE both count BuildNr up themselves: the program gets the number in the lpi, the lpi then holds the next one; never raise it by hand; pull before, then commit only the BuildNr line and push), run unit tests and the program where possible, and say plainly what was and was not tested. Cross compiling Windows <-> Linux does not work. In a chat without my computer nothing can be compiled: then I compile and send the messages.
7. Claude Prompt folder: the bundle zip contains the folder "Claude Prompt" inside PhotoDownloader/ (PhotoDownloader/Claude Prompt/; the zip has the single top-level folder PhotoDownloader/; no extra zip files inside it, no separate Claude_Prompt.zip). It holds the continuation prompts as text files (Claude-Prompt-N.txt). With every REVISION increment (every bundle from now on) a new prompt file named Claude-Prompt-<version>.txt is written (state, rules, features, open items; it is the same text as docs/Continuation_Prompt.txt at that moment), for example Claude-Prompt-58.txt for 0.1.0.58, Claude-Prompt-0.1.1.1.txt for 0.1.1.1 and Claude-Prompt-0.1.2.1.txt for the next one; the older prompt files (37, 42, 45, 50, 55, 58, ...) and Troubleshooting_Prompt.txt stay in the folder and the folder is included in every bundle. docs/Continuation_Prompt.txt is also updated for every delivery.
8. Beware: FPC set literals cannot hold values above 255; TBitmap has no FreeCanvasContext in my Lazarus; use {$POINTERMATH ON} for PByte indexing.
