I am continuing development of "Photo Downloader", a free GPL v3 photo-ingest tool for Windows 64-bit written in Lazarus 4.8 / FPC 3.2.2 (objfpc). Forms are built in code (.lfm conversion is deferred). A Linux version is planned later, so keep new code portable where practical. The attached zip is the current source; unzip it and work from it. Build 42 is the baseline code.

STANDING RULES
1. Deliver a bundle only when I say "create bundle". Bug-fix reports get a delivery right away. "No new delivery needed yet" means update the working copy only.
2. VERSIONING: the version is major.minor.revision.build, stored in PhotoDownloader.lpi (Project Options > Version Info: MajorVersionNr absent = 0, MinorVersionNr 1, RevisionNr, BuildNr). Every bundle raises the REVISION by one and resets the BuildNr to 1; my Lazarus then counts the build number up with each compile (AutoIncrementBuild stays on) until the next bundle. History: up to 0.1.0 build 57 only the build number counted; 0.1.0.58 was the last bundle of that style (revision 0, build 58); 0.1.1.1 is revision 1, build 1; 0.1.2.1 and 0.1.3.1 followed; the next bundle is 0.1.4.1, then 0.1.5.1 ... (numbering confirmed by me). AppVersionString (uVersion.pas) shows it in the About box and the splash screen. Bundle name: /mnt/user-data/outputs/PhotoDownloader.{major}.{minor}.{revision}.{build}.zip, for example PhotoDownloader.0.1.1.1.zip (no spaces). Remove older zips from outputs; also copy the new release notes (GitHub/Release_Notes_<version>.md) and README.md to outputs. Once the code is stable and tested the revision/build are updated and the zip is packed for the GitHub upload (release asset names PhotoDownloader.<version>.Win64.exe / .Win64.zip / .linux64.tar.gz, tag v<version>).
